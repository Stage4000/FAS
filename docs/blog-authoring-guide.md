# Preparing FAS blog content privately

The public blog is held until the owner explicitly releases it. Saving a draft or
a reviewed snapshot in the private admin area does not release the public blog.

## Start an article

Open **Blog** in the admin sidebar and choose **New post**. Enter a clear title,
short summary and author name. Choose a descriptive URL slug using lowercase
letters, numbers and single hyphens. The slug becomes permanent when the first
reviewed snapshot is saved, including if that snapshot is later removed.

Write in the visual editor. The first-party editor supports paragraphs, headings,
bold, italic, underline, single-level bullet and numbered lists, quotations,
website links and existing gallery images. Pasted text is treated as plain text.
HTML pasted into an article is not executable article markup.

Keep headings useful and use link text that explains its destination. Describe
images in their image-description field. A gallery image must still exist and be
readable when a reviewed snapshot is saved. This authoring workflow does not
upload or modify gallery files.

Use **Save draft** to store work. Typing and formatting alone are not a save.
**Preview saved draft** opens the most recently saved version, so save before
checking a new change. Preview is authenticated and is not a public share link.

## Review before a snapshot

Check technical claims, part identifiers, photos, links and related inventory
against reliable evidence. Do not infer fitment from a title or a similar-looking
part. Related products should help a reader and must not imply unsupported
compatibility. The final public renderer filters unavailable inventory.

Optional search title and description override the article title and summary.
If left blank, those article fields provide the fallback. Related inventory is
limited to six product IDs. Article text is limited to 60,000 visible characters;
an article may include at most 20 existing gallery images.

Confirm the factual/photo review checkbox and choose **Save reviewed publication
snapshot**. A recent password check is required. This stores the submitted article
as a reviewed snapshot while public release is held. Once the owner releases the
public blog through a separate release process, saved snapshots become eligible
for public display.

## Keep editing safely

Later **Save draft** actions do not change the reviewed snapshot. The status
**Draft changes after review** means the private draft and reviewed snapshot differ.
Review and save a new snapshot when the changes are ready.

**Remove reviewed snapshot** removes that snapshot and keeps the last saved draft
and reserved URL. Unsaved changes in the open form are not saved by removal. Once
the public blog is released, the equivalent action withdraws the public article.

If another administrator saves first, the editor rejects the stale save and
preserves the submitted text for comparison. Copy that work before reloading the
latest draft. Do not repeatedly submit the old revision.

If a save cannot be confirmed, check the saved draft before retrying. Reopening a
successful save shows its saved revision and recent activity. The activity list
records who performed an action and when; it is not a full-text version restore.

If the visual editor cannot safely convert older or invalid content, its source
remains visible rather than being replaced with an empty article. Preserve that
source and ask the site operator to review it before making structural changes.

## Access and release

Only current active administrators may use the authoring pages and previews.
Storage setup is an explicit, backed-up operator task. A storage-unavailable page
does not initialize or repair the database automatically.

There is no public-release switch in the editor. Public routes, sitemap entries,
navigation and the global release flag are managed in the separately reviewed
front-end release, with the owner's explicit approval.
