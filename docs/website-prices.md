## Approved cart policy

Observed baseline: cart prices live in browser localStorage; a reload retains those saved numbers. Product availability validation does not refresh prices. Classic server checkout reads current inventory, rejects changed unit prices/totals, and tells the shopper to refresh. Historical orders store their own amounts.

Approved behavior: no price lock for unpurchased carts. The cart checks current catalog prices, shows each old/new amount, and waits for **Accept current prices** before adopting those prices. It rechecks before acceptance and rejects concurrent cart edits. Accepting reloads the page to clear shipping estimates. Checkout remains authoritative and refuses stale prices, changed totals, invalid coupons or unavailable inventory; the shopper must review updated totals/shipping before paying. Existing completed orders and in-flight order/provider snapshots are not rewritten by override changes.

Acceptance writes a separate versioned USD price overlay bound to the exact persisted cart value. It never replaces the base cart, so even a write interleaved after the final read cannot erase another tab's quantities, additions or deletions. `ShoppingCart.loadCart` validates and applies the overlay on reload and checkout initialization; any base-cart change makes it inert. An ordinary later cart edit materializes the accepted prices using the existing save path. Ordinary cart edits retain their pre-existing last-writer-wins behavior; this change prevents the price-acceptance action from overwriting them. Deploy `main.js` and `cart-pricing.js` together.

Cart review and new wallet-attempt creation must enforce accepted prices per item, not merely compare the aggregate order total: offsetting price changes must also require renewed review. Existing created payment attempts retain immutable order amounts and their recovery behavior. The candidate does not claim a refresh alone updates saved cart prices. Fully styled browser, Buy Now, shipping/coupon invalidation and real provider lifecycle coverage remain limited. Use isolated evidence for mutation/payment flows; do not create production test orders or call live payment providers to close those limits. A separate staging website is not a default requirement.

New Apple/Google wallet attempts now require an explicit valid decimal `unit_price` on every submitted item and compare each one to the shared catalog price before any order/provider creation. Duplicate rows must supply identical prices. Existing owner/environment/wallet-bound attempts can recover their immutable old request hashes; missing per-item prices never authorize a new attempt. The shared checkout adapter supplies these prices for normal cart and Buy Now item state.

## Migration, backup and rollback gates

`scripts/install-website-prices.php --database /explicit/existing/path.sqlite` is CLI-only, requires an explicitly named existing file, uses native READWRITE without CREATE, and has no application-config default. It has not been run on a live database. It creates three additive tables and the nullable override column in one transaction, checks exact side-table DDL and migration marker, and refuses partial storage. New application code remains backward compatible with storage absent.

The installer uses a dedicated exception-mode SQLite PDO, temporarily sets `busy_timeout=0`, and restores its original numeric timeout in all confirmed cleanup paths. A custom busy-handler callback is outside this dedicated-connection contract: restoring a numeric timeout cannot reconstruct one. It uses raw `BEGIN IMMEDIATE`, `COMMIT` and `ROLLBACK` with explicit ownership tracking rather than depending on older PDO manual-transaction reporting. Schema is checked only after acquiring the writer, serializing competing installers.

There are at most three complete attempts in a monotonic 200ms contention retry window, with up to two 25ms backoffs. Only numeric SQLite BUSY (base code5) qualifies. Every retry follows confirmed full rollback; the installer never waits/retries COMMIT while holding its writer. LOCKED6, schema and I/O errors do not retry; unconfirmed rollback stops with an uncertainty error. A timeout-restoration error after confirmed COMMIT explicitly reports that the migration committed. This bounds lock waiting and retry scheduling, **not** native CHECK scans, filesystem fsync/rollback, OS scheduling, total runtime or writer-hold time. Measure those on a protected restored host backup before live execution; if they cannot fit normal service limits, revise the migration rather than taking the site offline.

Operator commands and outcomes:

```text
php scripts/install-website-prices.php --check --database /exact/existing/path.sqlite
php scripts/install-website-prices.php --database /exact/existing/path.sqlite
```

`--check` opens native READONLY with one explicit read snapshot and no lock wait. Exit0 means verified; exit3 means absent; exit75 means busy; exit1 means incompatible/not confirmed; exit2 means invalid usage or missing target. Installation reports elapsed milliseconds and explicitly says native DDL runtime is not bounded. On busy, do not wrap the command in an automatic shell retry loop. Inspect fresh read-only status and active writers first: verified needs no rerun; absent may be deliberately rerun after writers finish; incompatible or uncertain outcome requires reconciliation. Neither command creates a missing database.
