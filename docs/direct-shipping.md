# Direct shipping implementation

## Current scope

Direct domestic rate quoting and checkout shipping selection are implemented for USPS and UPS. Easyship remains the default provider. Client account onboarding has already been handled; this document covers application behavior and release controls, not account-registration instructions.

Both api/shipping-rates.php and api/shipping-estimate.php use the shared ShippingRateService. The checkout response retains courier_id, courier_name, service_name, total_charge, currency and delivery-time fields. Direct quotes add provider, service_code and rate_basis. Existing Easyship courier IDs are preserved and receive provider=easyship. Direct IDs must never be passed to Easyship's shipment API.

The free-shipping rules still run first. In Easyship mode, all-free carts keep their existing zero-charge method without a carrier call. In direct mode, all-free carts select a real USPS/UPS service with a zero customer charge and a separate private carrier estimate; if no direct service is available, checkout does not create an unfulfillable free-shipping order. Mixed carts charge the shopper only for the non-free items while obtaining a second, full-cart quote for label preparation. The selected service must exist for both scopes. The full-cart parcel snapshot and USPS label options are saved with the order; the two direct rating passes share one request deadline. Pre-checkout estimates also check that a full-cart direct service exists, though postal-only prices can differ from checkout. Product measurements and prices come from inventory, not submitted browser values. Both PayPal and Apple Pay use a ten-minute, session-bound shipping quote. Order creation rejects a changed cart, address, shipping price or method. Both payment paths now calculate the local order from catalog prices and validated coupons. PayPal completion additionally retrieves the captured order from PayPal and checks its local invoice reference, amount, destination and capture before inventory changes. A captured payment with insufficient stock is recorded as paid and pending review without a stock deduction; retrying it cannot report checkout success. This PayPal change has passed synthetic local tests; a sandbox payment, reload recovery and deployed checkout retest are still required before it can be treated as a release gate passed. Orders created by the previous checkout code have no bound PayPal invoice/custom reference and require manual reconciliation if they remain pending during deployment.

Rate quotes alone do not create orders or modify inventory. A pending order receives an immutable carrier/service/customer-charge/carrier-estimate/parcel snapshot in `order_shipping`; USPS selections also retain each parcel's rate indicator, processing category, price type and quoted charge. The separate `carrier_quote_cents` field lets an administrator confirm the actual label estimate when the shopper shipping charge is free or discounted. Carrier costs and label options stay in the server-owned quote and are omitted from the public rate response. This is shipping provenance, not a purchased label. Existing Easyship order rows remain readable through the additive schema migration. Direct label purchasing and cancellation are available only through authenticated administrator order workflows and have separate switches that are disabled by default. Read-only tracking polling and transactional customer tracking notifications have separate disabled switches. Pickup booking and automatic fulfillment are not implemented yet.

The private shipping database has a fulfillment-operation ledger. It reserves one operation per USPS parcel or one UPS multi-package shipment, tied to a paid processing order and its saved parcel/address fingerprint. An active administrator must verify their password, pass CSRF validation and explicitly confirm the saved carrier charge before purchase. OAuth and USPS payment authorization are prepared before the operation is marked submitted. A submitted operation sends at most one label request; an ambiguous result stays in review and cannot trigger another request. A confirmed response atomically saves every package tracking number and label image in that private database; a failed save leaves the operation in review with no partial labels. Label downloads check the administrator's current account status and each image's digest. The [USPS Labels API](https://developers.usps.com/domesticlabelsv3) requires a separate payment-authorization token and names its UUID header `X-Idempotency-Key`, but explicitly says repeating a label POST with that UUID can create another label. The UUID supports reprint/cancellation lookup; only the local one-send ledger prevents a repeated purchase. The [UPS Shipping specification](https://github.com/UPS-API/api-documentation/blob/main/Shipping.yaml) describes a request transaction identifier but does not document it as purchase idempotency. Lost responses need carrier reconciliation before any new shipment request.

The [USPS Payments API](https://devs.usps.com/paymentsv3) states that payment authorization tokens remain valid for eight hours and should be reused across labels. The application caches them in the private shipping database for seven hours, keyed by the USPS account, application and environment. A new account or expired cache entry obtains a new token before an action; a failed label purchase is still never retried automatically. Cache behavior passed local synthetic tests and needs sandbox acceptance with the actual account.

A different active administrator can take over an untouched `reserved` label operation after 15 minutes. The original operation and carrier reference remain intact, and the transfer is recorded in `shipping_label_handoffs`. The price and request are validated before the handoff; if its audit write fails, the old operator remains assigned. Only the current operator can mark the operation submitted. The administrator page shows when a recent reservation becomes available, offers an explicit takeover for an aged one, and displays the latest handoff. Neither `submitted` nor `review` operations can be transferred or sent again. Run the private `init` migration before enabling label purchases so the handoff ledger exists.

For an uncertain USPS purchase, an administrator can request the original label through USPS's separate reprint endpoint using the saved purchase key. This path has its own `label_reprint_enabled` switch, initially false. It requires a paid processing order, the same carrier environment, an active administrator's password and CSRF token, an original submission at least 15 minutes old, no cancellation request, and a saved mailing date that has not passed in UTC. The private `shipping_label_reprints` table claims one request before calling USPS. A successful response must contain valid label metadata, image, tracking number and postage before the original operation becomes ready; a failed or uncertain reprint remains in review and is never sent again automatically. This does not create another label purchase. USPS documents that reprints are limited to the mailing date and a maximum of three, and that repeating the original label POST can create another label. The path has synthetic local coverage only; leave it disabled until the account's sandbox response and reprint limits are verified. UPS uncertain purchases still require carrier-account reconciliation. [USPS Labels API](https://developers.usps.com/domesticlabelsv3).

An administrator can record the original USPS or UPS labels after independently confirming an uncertain purchase in the carrier account. The `shipping-label-reconcile.php` page requires the original submission to be at least 15 minutes old, a paid processing order, current password, CSRF, explicit carrier-evidence confirmation, the final carrier charge, exact tracking numbers and the original PDF/GIF for every package. It refuses canceled shipments and a recent USPS reprint that might still finish. This action makes no carrier request and does not authorize a replacement purchase. Validated labels, charge and the administrator's carrier case/confirmation reference are saved atomically in private storage; stale or duplicate reviews cannot overwrite the result. A missing review migration disables the form. Configure PHP uploads to accept the selected files within the page's 7 MB combined limit, and verify the downloaded labels before shipping. The workflow has local synthetic service and HTTP coverage; carrier-account and deployment acceptance remain pending.

Label preparation builds USPS and UPS request bodies from paid order records, saved destination/origin addresses and packed parcels. It rejects missing or carrier-incompatible details before a purchase attempt. A bounded HTTPS transport sends one request and bounded response parsers validate USPS multipart metadata/PDF or each UPS package's tracking number, GIF and billed USD amount. The administrator page at `admin/shipping-label.php` shows the saved service, addresses, parcel measurements, quote and operation state; confirmed labels are downloaded through `admin/shipping-label-download.php`. The read-only `admin/shipping-operations.php` queue lists uncertain outcomes so operators can find them without retrying the purchase.

For USPS, each saved parcel also retains its retail or commercial quote tier. The label endpoint's [published request example](https://github.com/USPS/api-examples#domestic-label-request) does not include a `priceType` field, so the purchase request does not invent one. Before a new label operation is reserved, the application requires the saved tier to match the configured USPS tier and validates its positive parcel quote. The administrator page shows the saved tier and holds purchase if that configuration changed after checkout. This guards against a silent settings drift, but the carrier's billed amount can still differ from the earlier estimate; the operator must inspect the returned charge and label before shipping. Confirm the account's actual tier and surcharge behavior in sandbox before enabling purchases.

An active administrator can review a confirmed direct label at `admin/shipping-label-cancel.php`. After CSRF, password and explicit unused-label confirmations, a separate private ledger claims at most one carrier cancellation request. USPS can confirm cancellation or return a refund request, which remains pending until carrier confirmation. UPS voids the entire saved shipment. An uncertain response stays in review and is never resent automatically. Once a cancellation has been recorded, label downloads are unavailable; follow-ups appear in the shipping review queue. These controls passed synthetic service, HTTP and rendered-page checks, but no carrier sandbox cancellation has been made. Keep both `label_purchasing_enabled` and `label_cancellation_enabled` false on the production host pending carrier acceptance and deployed verification. [USPS Labels API](https://developers.usps.com/domesticlabelsv3); [UPS Shipping specification](https://github.com/UPS-API/api-documentation/blob/main/Shipping.yaml).

The `refresh-tracking` CLI command polls at most 20 confirmed, uncancelled package numbers per invocation. A private per-package lease prevents simultaneous workers from polling the same number. Successful status checks are eligible again after 30 minutes; failures wait at least 15 minutes, and a carrier 429 backs off that carrier for the supplied retry interval. Only a short status and check time are retained; raw tracking responses, customer names, addresses and signatures are discarded. The administrator label page shows saved status for each package. Polling covers labels created within the previous 120 days and is disabled by default for each carrier. It has passed synthetic USPS/UPS status and browser checks, but it is not yet carrier-approved or scheduled on deployment. [USPS Tracking 3.2](https://developers.usps.com/trackingv3r2); [UPS Tracking specification](https://github.com/UPS-API/api-documentation/blob/main/Tracking.yaml).

Shipping Review now monitors the same recent, confirmed, uncancelled package scope. It flags failed polls, an interrupted check after 15 minutes, an absent first update after 30 minutes and a last successful status older than 24 hours. Aggregate counts remain complete while the table shows at most 50 of the oldest follow-ups. A disabled polling configuration is displayed explicitly; missing storage is shown as unavailable rather than a healthy zero. These are local operational signals, not delivery outcomes or independent proof of a carrier outage. Page refresh only reads storage and never polls carriers, sends email or changes fulfillment. Customer email follow-ups and recent reconciliation history are available on the same page.

## Recording verified cancellation outcomes

The existing cancellation page now supports local reconciliation after checking the shipment in the carrier account or with carrier support. An active administrator must re-enter their password, pass CSRF validation, confirm the exact tracking number and provide a carrier case or confirmation reference. The form records either confirmed cancellation or, for USPS, an accepted refund request that remains pending. It makes no carrier call and works with the carrier cancellation switch disabled.

Only uncertain results, pending refund requests and submissions older than 15 minutes are eligible. Operators must confirm that the original request is no longer running. A pending USPS request can later become a confirmed cancellation, preserving both review records. Stale or repeated forms cannot overwrite a completed outcome. Recording cancellation does not establish that a financial refund was received; credits must be checked separately in the carrier account. Denied or still-unknown outcomes remain in review and require operational follow-up; this workflow does not authorize replacement labels.

Run `php scripts/shipping-maintenance.php init` after backing up the private shipping database to add `shipping_cancellation_resolutions`. Existing rows and original operator information are preserved. Each review stores the previous state, outcome, evidence reference, administrator ID and UTC time in the same transaction as the status change. Missing history storage disables reconciliation. Health and readiness report whether the review table exists. Confirmed cancellations leave the follow-up queue; their history remains available through the order's label cancellation page. Label downloads, tracking polling and customer notifications remain blocked for every recorded cancellation request.

## Provider behavior

USPS uses OAuth v3 and Domestic Prices v3 base-rates-list/search. It requests Ground Advantage, Priority Mail and Priority Mail Express, then accepts only supported ordinary customer-package options. It excludes flat-rate packaging, restricted-content classes, cubic tiers and destination-entry discounts. Each separately packed unit is charged; a service is returned only if it covers every parcel. Published retail pricing is the default. Commercial pricing requires separate operational/account verification. See the [USPS pricing specification](https://developers.usps.com/domesticpricesv3) and [official API examples](https://github.com/USPS/api-examples).

USPS currently documents both gateway families. The configured gateway must match the issued application's environment; credentials are not interchangeable between test and production. The supported fixed hosts are apis.usps.com / apis-tem.usps.com and api.usps.com / api-cat.usps.com. See [USPS gateway guidance](https://devs.usps.com/getting-started).

UPS uses client-credentials OAuth and Rating v2409 Shop. It sends measured packages and the shipper account, preferring a returned negotiated shipment total over published pricing. A published quote remains explicitly identified when no negotiated total is returned. Destinations are rated residential because the storefront does not yet have verified commercial-address classification. Detected PO boxes are excluded from UPS. See the official [UPS Rating specification](https://github.com/UPS-API/api-documentation/blob/main/Rating.yaml) and [OAuth specification](https://github.com/UPS-API/api-documentation/blob/main/OAuthClientCredentials.yaml).

No delivery-day promise is inferred from a service name. The first version displays Delivery estimate unavailable. Prices are estimates, and account-specific invoice reconciliation remains part of activation testing.

## Packing and geography

- Direct quoting covers the 50 US states and DC. International, military and territory routes remain outside this initial direct rollout.
- Each inventory unit represents one independently packed parcel. This is an explicit packing policy, not a box-consolidation algorithm. Confirm that catalog dimensions and weights describe packed parcels before setting parcel_data_verified.
- Direct quotes save the measured parcel edges in descending order as length, width and height, as required by the [USPS pricing specification](https://developers.usps.com/domesticpricesv3). Label requests apply the same ordering to earlier saved parcels. No measurement or package count is changed.
- Missing measurements, unsupported dimensions, nonfinite values, more than ten parcels, unavailable origins and mixed origin addresses are refused by the direct path. Legacy 1 lb / 10-inch defaults cannot become direct quotes.
- Assigned origins are resolved per product. An inactive or missing assigned warehouse cannot silently become another warehouse. Unassigned products require exactly one active default warehouse; direct quotes do not select an arbitrary active warehouse. Administrator warehouse changes require an active account and CSRF token. Selecting a new default clears the old one in the same SQLite transaction; failed changes preserve the existing default.
- USPS parcels over 70 lb or 130 inches in combined length and girth are refused before cache reuse or carrier calls. Parcels over 108 but no more than 130 inches may request only Ground Advantage; Priority Mail and Priority Mail Express stop at 108 inches. Label preparation repeats the selected service's limit for saved orders. The catalog scan flags USPS-only size and weight exceptions separately because an otherwise valid parcel may still qualify for UPS. See [USPS Ground Advantage](https://www.usps.com/ship/ground-advantage.htm), [Priority Mail](https://www.usps.com/ship/priority-mail.htm) and [Priority Mail Express](https://www.usps.com/ship/express-mail.htm). General direct parcel bounds also apply. Nonstandard contents, special services, extra insurance, packing overrides and multi-origin fulfillment require further work.
- Postal estimates omit street lines from direct requests. Checkout rates use the actual submitted street address and may differ from the preliminary estimate.

## Configuration and release controls

Configuration lives in src/config/shipping.php, separate from ordinary settings-file rewrites. The file is ignored by Git. The example is src/config/shipping.example.php. An operator may instead select a deployment-owned file with FAS_SHIPPING_CONFIG_PATH. Secrets can be supplied through the environment variables named in the example; do not put credentials in tracked files.

| Mode | Behavior |
|---|---|
| easyship | Existing provider only; no new cache initialization or carrier credentials required |
| direct_with_fallback | Return successful activated direct rates; query Easyship only if none are available |
| direct | Return activated direct rates only; unavailable quotes remain unavailable, never free |

Each direct carrier must be enabled, have credentials present, use environment=production and have production_verified=true before it can supply public checkout rates. Sandbox adapters can be exercised by the test/staging harness, but sandbox rates are never surfaced by the public service. One carrier can be activated before the other.

Label purchasing has a separate `label_purchasing_enabled` switch for each carrier, initially false. The administrator purchase path also requires a verified shipper name, a phone and billing account for UPS, and USPS CRID/MID/manifest MID/EPS account values for its payment token. Production label purchasing requires `production_verified=true`. Keep the purchase switch off until carrier sandbox requests, cost reconciliation, label retrieval and failure recovery are verified. The operator must manually review any operation left in `submitted` or `review`; the application never reissues that shipment request.

Cancellation has its own `label_cancellation_enabled` switch for each carrier, initially false and independently gated by verified production configuration. Keep it off until unused-label eligibility, void/refund responses, ambiguous outcomes and reconciliation are exercised with each carrier account. A refund-request reference is evidence of a request, not proof that a refund was issued. An operation left in `submitted` or `review` must be reconciled in the carrier account; do not send another DELETE. A `reserved` operation indicates preparation before the carrier action and can be resumed only by the same administrator after checking its state.

Tracking uses a separate `tracking_enabled` switch for each carrier, initially false. Run `init` to add private tracking storage before using `refresh-tracking`. Enable polling only after the issued account has access to the tracking API and sandbox response shapes, throttling and expected volume have been checked. Do not present a missing or failed status check as a delivery outcome. Customer tracking notifications are implemented locally; controlled inbox verification and production activation remain pending. See [the notification runbook](shipping-notifications.md).

Activation requires verifying packed catalog data, warehouse addresses, account rate permissions, applicable pricing, USPS gateway, sufficient API quota, expected surcharges and representative destinations. Credential presence or a healthy cache does not establish successful carrier authentication. Leave Easyship mode active while credentials and verification are pending.

## Private cache and operations

The rate and estimate endpoints check the migrated order table before offering direct services. Direct-only mode returns a temporary-unavailable response if that storage is missing; direct-with-fallback keeps Easyship available until migration is complete. The CLI readiness report distinguishes an existing historical `order_shipping` table from one with the new carrier-estimate field.

Set FAS_SHIPPING_CACHE_PATH to an absolute SQLite path outside the application/public web root. Its parent directory must already exist with access restricted to the PHP/CLI service identity. On Unix, use an owner-only directory and file permissions; on Windows, restrict the directory ACL. Initialize under the same service identity that will run PHP.

~~~sh
php scripts/shipping-maintenance.php init
php scripts/shipping-maintenance.php health
php scripts/shipping-maintenance.php readiness
php scripts/shipping-maintenance.php cleanup
php scripts/shipping-maintenance.php refresh-tracking
~~~

CLI `init` creates the private `shipping_cache`, `shipping_label_operations`, `shipping_label_handoffs`, `shipping_label_reprints`, `shipping_label_resolutions`, `shipping_label_packages`, `shipping_label_cancellations` and `shipping_tracking` tables and the additive `order_shipping` table, including the separate carrier estimate. It adds the expected package count to an existing operation ledger; older operations with an unknown package count cannot be finalized through the new review form and require separate carrier-account investigation. `init-orders` initializes just the order table if the private cache is not configured yet. Public direct requests require initialized storage. Health reports configuration readiness, order-storage presence, cache health, reservation-handoff, USPS reprint and carrier-evidence review storage, fulfillment/cancellation counts, tracking status counts and stored package labels without secrets or account numbers; it makes no external API call. `refresh-tracking` makes no carrier request when the per-carrier switch is off. Cleanup removes at most 200 expired cache rows per invocation. The cache is capped at 1,000 records; fulfillment operations, handoff history, cancellations, tracking statuses and labels are durable and never pruned by cache cleanup.

The October 2 notification update also installs `shipping_notifications`, `shipping_notification_scans` and `shipping_notification_resolutions`, and adds nullable carrier-environment provenance to label operations and tracking results. Run `init` before resuming label or tracking workers on this version. Existing labels retain unknown provenance and cannot produce customer emails automatically. Back up private shipping and inventory databases before this additive migration.

`readiness` reports local carrier configuration blockers, storage availability, notification settings and outstanding external acceptance work. Its separate `fulfillment_storage_configured` field requires label storage, the handoff migration and the carrier-evidence review ledger; `reprint_storage_configured` reports the optional USPS recovery ledger. These fields do not claim a carrier purchase was verified. It also scans currently saleable products for numeric parcel measurements, direct-carrier size bounds and usable origins, with at most 20 product IDs per issue. USPS parcels over 70 lb or 130 inches in length and girth are reported separately as carrier-specific exceptions. Multiple origin addresses are flagged because mixed-origin carts are not supported; a single-origin cart may still be valid. A successful data scan does not verify that measurements describe actual packed parcels. It makes no carrier or mail request, creates no missing inventory database and never marks production acceptance complete. A healthy report cannot establish real carrier access, inbox delivery or a successful checkout.

The read-only `/admin/shipping-readiness.php` page gives active administrators the local mode, carrier blockers, private quote/order storage state, installed label/recovery/cancellation/tracking/email records and saleable catalog issues without displaying credentials or calling a carrier. Its example product links open the existing editor; the inventory section also links to warehouse management. Product editing now identifies weight and dimensions as the packed parcel for one unit, including packaging. Bulk shipping values should be used only when the selected products truly share those measured package dimensions. Installed storage is an operational preparation check, not proof of carrier acceptance or enabled customer messages.

The `shipping_cache` table stores OAuth tokens, normalized rates and provider cooldowns. Quote keys hash the complete shipment and carrier configuration, including credential/environment changes. Street addresses, client secrets and raw response bodies are not stored in that cache table. The same private database can store purchased label images, which contain recipient details, so protect and back up the entire file as both secret and customer-data storage. It is separate from inventory and payment transactions.

Tokens expire before the carrier's reported expiry. Quotes expire after three minutes by default. A 401 permits one token refresh/retry; a second failure stops. Provider 429 Retry-After values produce a shared cooldown, and authentication/server failures also back off. No background retry loop is introduced. Per-request transport timeouts are at most six seconds with an eighteen-second default budget for direct requests. Existing Easyship timeout/retry behavior is unchanged and is outside that direct-request budget.

Direct transport uses fixed HTTPS hosts, certificate verification, no redirects and a one-megabyte response limit. Direct provider errors omit request/response bodies, addresses and credentials. Endpoint monitoring also records counts/provider status instead of submitted customer payloads. Existing logging inside the legacy Easyship adapter is unchanged.

To roll back carrier selection, restore mode=easyship. Preserve the private cache and order selection records unless doing a coordinated code rollback. No inventory or order rollback is needed.
